## שלב 0: הקמת פרויקט מקצועי

### Git ו-GitHub
| מושג | הסבר |
|---|---|
| **Repository (מאגר)** | תיקיית הפרויקט יחד עם כל היסטוריית השינויים שלה |
| **Commit** | "נקודת שמירה" עם תיאור. כל commit הוא צילום של מצב הקוד |
| **Branch (ענף)** | קו פיתוח נפרד. עובדים על שלב בענף משלו, בלי לשבור את `main` |
| **Push** | העלאת ה-commits מהמחשב ל-GitHub |
| **Pull Request (PR)** | בקשה למזג ענף ל-`main`. המקום לסקירה, לדיון ולהרצת CI |
| **Conventional Commits** | פורמט קבוע להודעות: `feat:` לתכונה, `fix:` לתיקון, `docs:` לתיעוד |

### מבנה פרויקט Python
| מושג | הסבר |
|---|---|
| **`pyproject.toml`** | "תעודת הזהות" של הפרויקט: שם, גרסה, תלויות והגדרות כלים, בקובץ אחד |
| **src layout** | הקוד יושב ב-`src/knowledge_journey/`. כך הבדיקות רצות מול החבילה המותקנת, ולא מול קבצים מפוזרים |
| **סביבה וירטואלית (`.venv`)** | התקנה מבודדת של ספריות לפרויקט, כדי שלא יתנגשו עם פרויקטים אחרים |
| **uv** | כלי מהיר שמנהל גם את גרסת Python, גם את הסביבה וגם את התלויות |
| **Lockfile (`uv.lock`)** | רשימה של **הגרסאות המדויקות** שהותקנו, כדי שכל מחשב (וה-CI) יקבל אותה סביבה בדיוק |
| **`py.typed`** | קובץ ריק שמסמן שהחבילה כוללת type hints |

| כלי | מה הוא עושה | דוגמה |
|---|---|---|
| **ruff** (lint) | מוצא באגים אפשריים וקוד לא תקין | משתנה שהוגדר ולא בשימוש |

### CI ו-pre-commit
- **CI (Continuous Integration):** בכל push או PR, ‏GitHub Actions מקים מחשב נקי, מתקין ומריץ את כל הבדיקות. אם משהו נכשל, רואים ❌ ב-PR. כך "אצלי זה עובד" כבר לא תירוץ.
- **Matrix:** אותן בדיקות רצות על Python 3.12 וגם על 3.13.
- **pre-commit:** הבדיקות רצות **אצלך** לפני כל commit, כך שבעיות נתפסות עוד לפני שהן מגיעות ל-GitHub. בין השאר הוא בודק שלא נכנס בטעות מפתח סודי.

### תיעוד ועבודה עם סוכן AI
- **`CLAUDE.md`:** הזיכרון של סוכן הפיתוח. כל שיחה חדשה מתחילה בקריאה שלו: עקרונות, פקודות ומוסכמות. **זה ההבדל בין "צ'אט" לבין עבודה מסודרת עם סוכן.**
- **ADR (Architecture Decision Record):** מסמך קצר לכל החלטה חשובה: מה ההקשר, מה החלטנו, ומה המחיר. בעוד שנה ידעו *למה* הקוד בנוי כך.
- **Mermaid:** תרשימים שנכתבים כטקסט ומוצגים כציור ב-GitHub.
