### CI ו-pre-commit
- **CI (Continuous Integration):** בכל push או PR, ‏GitHub Actions מקים מחשב נקי, מתקין ומריץ את כל הבדיקות. אם משהו נכשל, רואים ❌ ב-PR. כך "אצלי זה עובד" כבר לא תירוץ.
- **Matrix:** אותן בדיקות רצות על Python 3.12 וגם על 3.13.
- **pre-commit:** הבדיקות רצות **אצלך** לפני כל commit, כך שבעיות נתפסות עוד לפני שהן מגיעות ל-GitHub. בין השאר הוא בודק שלא נכנס בטעות מפתח סודי.

### תיעוד ועבודה עם סוכן AI
- **`CLAUDE.md`:** הזיכרון של סוכן הפיתוח. כל שיחה חדשה מתחילה בקריאה שלו: עקרונות, פקודות ומוסכמות. **זה ההבדל בין "צ'אט" לבין עבודה מסודרת עם סוכן.**
- **ADR (Architecture Decision Record):** מסמך קצר לכל החלטה חשובה: מה ההקשר, מה החלטנו, ומה המחיר. בעוד שנה ידעו *למה* הקוד בנוי כך.
- **Mermaid:** תרשימים שנכתבים כטקסט ומוצגים כציור ב-GitHub.

## שלב 1: מודל הנתונים והתבנית

### הרעיון המרכזי: טעינה היא בדיקה
קובץ משחק (JSON) נטען למחלקות Python שמתארות מה מותר. אם משהו לא תקין, הטעינה נכשלת **מיד**, עם רשימת שגיאות, ולא באמצע שיעור מול הכיתה.

```python
class Question(StrictModel):
    answers: list[NonEmptyStr] = Field(min_length=4, max_length=4)
    correct_index: int = Field(ge=0, le=3)
    rationale: NonEmptyStr
```

### מושגים
| מושג | הסבר | איפה בקוד |
|---|---|---|
| **מודל נתונים** | הגדרה מדויקת של הישויות (משחק, תחנה, שאלה) ושל הקשרים ביניהן | `models.py` |
| **Pydantic** | ספרייה שהופכת type hints לבדיקות בזמן ריצה | `BaseModel`, `Field` |
| **ולידציה** | בדיקה שהנתונים עומדים בכללים. שדה בודד: `Field(min_length=4)`. כלל בין שדות: `@model_validator` | `Station._check` |
| **`extra="forbid"`** | שדה לא מוכר הוא שגיאה. כך שגיאת כתיב (`rationel`) לא "מעלימה" נימוק בשקט | `StrictModel` |
| **Enum** | רשימה סגורה של ערכים אפשריים, למשל `learning` או `review` | `Mode`, `StationKind` |
| **Discriminated Union** | שלב יכול להיות אחד מכמה סוגים. השדה `type` אומר ל-Pydantic איזה מהם | `Step` |
| **JSON Schema** | תיאור של מבנה JSON בפורמט סטנדרטי, שגם JavaScript מבין. מקור אמת אחד לנגן ולסטודיו | `schema/game.schema.json` |
| **CLI ו-exit code** | פקודה בטרמינל. קוד יציאה 0 = הצלחה, אחר = כישלון, כך ש-CI וסקריפטים יודעים מה קרה | `cli.py` |
| **pytest fixture** | פונקציה שמכינה נתונים לבדיקה. כל בדיקה מקבלת עותק טרי של המשחק לדוגמה ו"שוברת" כלל אחד | `conftest.py` |

### שלוש החלטות עיצוב, ולמה
1. **"מצב לא חוקי שאי אפשר לייצג".** שאלת העוגן נשמרת פעם אחת, ותחנות 1 ו-7 רק *מפנות* אליה (`{"type": "anchor"}`). לא צריך לבדוק שהן זהות, כי הן פשוט לא יכולות להיות שונות. באותו אופן, "תשובה נכונה אחת" מובטחת כי נשמר רק מספר אחד (`correct_index`).
2. **טבלת כללים במקום אחד.** הדרישות לכל תחנה (משך, מספר שאלות) נמצאות ב-`template.py`. כשהלקוחה תענה על המבנה של תחנות 4–6, נשנה שורה אחת.
3. **מדיה כנתיב יחסי בלבד.** קישור לאינטרנט נדחה, כי הנגן חייב לעבוד בלי רשת (ADR 0001).

### בדיקה שמונעת "שתי גרסאות"
הבדיקה `test_committed_schema_is_up_to_date` משווה את קובץ ה-Schema השמור למה שהקוד מייצר. מי שישנה מודל וישכח להריץ `kj schema` יקבל ❌ ב-CI.

### 🧪 תרגול מעשי
להריץ את `kj validate` על המחשב שלך, לשבור את המשחק לדוגמה בכוונה ולראות את ההודעות: [`RUN-LOCALLY.md`](RUN-LOCALLY.md).

### 🔁 שאלות חזרה
1. מה ההבדל בין בדיקה ב-`Field(...)` לבין בדיקה ב-`@model_validator`? תני דוגמה לכל אחת מהקוד.
2. למה לא בדקנו "שאלת העוגן זהה בתחנה 1 ובתחנה 7" עם `if`, ומה עשינו במקום?
3. מה היה קורה בלי `extra="forbid"` אם מורה הייתה כותבת `"rationel"`?
4. מה תפקיד השדה `type` בכל שלב?
5. אילו כללים ה-JSON Schema **לא** יכול לבדוק, ואיפה הם נבדקים?
6. איזה קובץ צריך לשנות אם הלקוחה תחליט שבתחנת "מפצחים" יהיו חמש חידות?

## שלב 2ב: מודל הנתונים לפי האפיון (גרסת סכימה 2)

### הרעיון המרכזי: מבנה במקום ספירה
בשלב 1 כל תחנה הייתה "רשימת שלבים" כללית, וכלל נפרד **ספר** כמה שאלות יש בה. עכשיו לכל תחנה יש **מודל משלה עם שדות בשמות**:

```python
class DiscoverStation(StrictModel):
    identify: Key  # מזהים
    understand: Key  # מבינים
    distinguish: Key  # מבחינים
```

אי אפשר לכתוב תחנת "מגלים" עם שני מפתחות או עם ארבעה. המבנה עצמו לא מאפשר את זה. זה אותו עיקרון כמו שאלת העוגן בשלב 1: **מצב לא חוקי שאי אפשר לייצג**. בונוס: קובץ המשחק קריא יותר, כי כתוב בו `"locks"` ולא `"steps"`.

### מושגים
| מושג | הסבר | איפה בקוד |
|---|---|---|
| **הרכבה (Composition)** | מודל שמורכב ממודלים קטנים: `Game` מכיל `Stations`, שמכיל `CrackStation`, שמכיל `Lock`, שמכיל `Question` | `models.py` |
| **מודל לשימוש חוזר** | `Content` (טקסט, מדיה או שניהם) מופיע בכל מקום שמוצג בו משהו על המסך: ידע, דוגמה, תוצאת הכרעה | `Content` |
| **שדה אופציונלי** | `confirm_question: Question \| None = None`: אם המורה לא כתבה שאלת אישור, עוברים למסלול המונחה | `Key`, `Lock` |
| **הפרדה בין מבנה למספרים** | *מה* יש בכל תחנה נמצא ב-`models.py`. *כמה זמן ונקודות* נמצאים ב-`template.py`. שינוי של ברירת מחדל לא נוגע במבנה | ADR 0004 |
| **גרסת סכימה** | `schema_version: 2`. קובץ ישן (גרסה 1) נדחה עם הודעה ברורה, במקום להיטען חלקית | `Game` |
| **הפניות בין חלקים** | מזהים (`media_id`, `central`) מחברים בין חלקים. הוולידציה בודקת שכל הפניה מובילה למשהו קיים, ושסרטון הפתיחה הוא באמת סרטון | `Game._check` |

### 🔁 שאלות חזרה
1. למה עדיף `identify`, `understand` ו-`distinguish` על פני `keys: list[Key]` עם `min_length=3`?
2. אילו בדיקות **עדיין** צריך לכתוב ב-`@model_validator`, גם כשהמבנה קבוע? (רמז: הפניות, ייחודיות)
3. בתחנה 4 יש `tie_default` עם `le=1`. למה דווקא 1?
4. אם הלקוחה תחליט שבסבב המהירות יהיו 5 שאלות, אילו שני קבצים צריך לשנות?
5. למה `Content` דורש טקסט **או** מדיה, ולא את שניהם?
